## 一、为什么需要结构化提示词

### 1.1 低效提问 vs 高效提问对比

**❌ 低效提问示例：**

```
用户：帮我写个用户登录接口
```

**AI 输出问题：**
- 不知道用什么框架（SpringBoot？Express？）
- 不知道数据库类型（MySQL？MongoDB？）
- 不知道认证方式（JWT？Session？）
- 代码风格不统一
- 缺少异常处理
- 没有注释和文档

---

**✅ 高效提问示例：**

```
你是一位资深 Java 后端工程师，精通 SpringBoot 3.2 + MyBatis-Plus。

请按照以下要求生成用户登录接口代码：

【技术栈】
- Java 17
- SpringBoot 3.2
- MyBatis-Plus 3.5
- JWT 认证
- MySQL 8.0

【业务需求】
1. 接收用户名和密码
2. 验证用户是否存在
3. 密码使用 BCrypt 加密比对
4. 生成 JWT Token（有效期 24 小时）
5. 记录登录日志

【代码规范】
- 遵循阿里巴巴 Java 开发手册
- 添加完整的 JavaDoc 注释
- 统一异常处理
- 参数校验使用 @Valid

【输出格式】
1. Controller 层代码
2. Service 层代码
3. Entity 实体类
4. 统一的响应结果封装类
```

**AI 输出优势：**
- ✅ 技术栈明确，代码可直接运行
- ✅ 符合企业编码规范
- ✅ 包含完整的分层架构
- ✅ 有异常处理和参数校验
- ✅ 代码风格统一

---

### 1.2 结构化提示词的价值

| 维度 | 非结构化提问 | 结构化提问 |
|------|------------|-----------|
| **代码可用性** | 30%（需大量修改） | 90%（微调即可） |
| **开发效率** | 低（反复调整） | 高（一次到位） |
| **代码质量** | 不稳定 | 稳定可控 |
| **学习成本** | 高（需要甄别） | 低（规范统一） |
| **团队协作** | 困难（风格不一） | 容易（标准统一） |

## 二、提示词四大核心要素

### 2.1 核心要素模型

```
优质提示词 = 角色（Role）+ 任务（Task）+ 格式（Format）+ 约束（Constraint）
```

---

### 2.2 要素详解

#### 1️⃣ 角色（Role）- 你是谁？

**作用：** 激活大模型的特定领域知识

**后端工程师常用角色：**

```markdown
# 基础角色
- "你是一位资深 Java 后端工程师"
- "你是一位 MySQL 数据库专家"
- "你是一位微服务架构师"

# 进阶角色（更具体）
- "你是一位有 10 年经验的电商系统架构师，精通高并发场景"
- "你是一位金融级系统安全专家，擅长数据加密和权限控制"
- "你是一位性能优化专家，擅长 JVM 调优和 SQL 优化"
```

**💡 技巧：** 角色越具体，输出越专业

---

#### 2️⃣ 任务（Task）- 要做什么？

**作用：** 明确具体需求和目标

**任务描述要点：**
- 清晰说明业务场景
- 列出功能清单
- 指定输入输出
- 说明边界条件

**示例：**

```markdown
【任务】
设计一个订单查询接口，支持以下条件筛选：
1. 按订单号精确查询
2. 按时间范围查询（开始时间 - 结束时间）
3. 按订单状态查询（待支付/已支付/已取消）
4. 支持分页（默认每页 20 条）

【输入】
- orderId: String（可选）
- startTime: LocalDateTime（可选）
- endTime: LocalDateTime（可选）
- status: Integer（可选）
- pageNum: Integer（默认 1）
- pageSize: Integer（默认 20）

【输出】
- 订单列表（包含订单基本信息）
- 总记录数
- 当前页码
- 总页数
```

---

#### 3️⃣ 格式（Format）- 如何输出？

**作用：** 规范输出结构，便于直接使用

**常用输出格式：**

```markdown
【输出格式要求】
1. 代码部分：
   - 按分层结构输出（Controller → Service → Mapper → Entity）
   - 每个类单独代码块
   - 添加必要的注释

2. 文档部分：
   - 使用 Markdown 表格
   - 接口文档包含：URL、Method、Request、Response、Error Codes

3. SQL 部分：
   - 提供 EXPLAIN 执行计划分析
   - 标注索引建议
```

---

#### 4️⃣ 约束（Constraint）- 有什么限制？

**作用：** 限定输出范围，避免偏离需求

**常见约束类型：**

```markdown
【技术约束】
- 必须使用 Java 17 新特性（Record、Switch Expression）
- 禁止使用 Lombok，使用原生 Getter/Setter
- 数据库操作必须使用 MyBatis-Plus，禁止原生 MyBatis XML

【业务约束】
- 密码必须使用 BCrypt 加密
- Token 有效期不能超过 24 小时
- 敏感字段（手机号、身份证）必须脱敏

【性能约束】
- 接口响应时间 < 200ms
- 单次查询返回数据不超过 1000 条
- 必须添加数据库索引

【安全约束】
- 防止 SQL 注入（使用预编译）
- 防止 XSS 攻击（参数转义）
- 添加接口限流（单用户 QPS < 10）
```

### 3.2 角色切换技巧

**场景：** 同一个问题需要多角度分析

```markdown

"作为微服务架构师，这个业务应该如何拆分服务？"

# 第二步：以 DBA 视角优化

"最后作为 Java 工程师，生成具体的代码实现"
```

**💡 优势：** 获得全方位的专业建议

## 四、代码类提示词精准写法

### 4.1 完整代码生成模板

```markdown
# 角色
你是一位资深 Java 后端工程师

# 任务
生成一个完整的用户注册功能模块

# 技术栈
- Java 17
- SpringBoot 3.2.0
- MyBatis-Plus 3.5.5
- MySQL 8.0
- JWT 0.11.5
- Hibernate Validator 8.0

# 业务需求
1. 用户注册（用户名、密码、手机号、邮箱）
2. 用户名唯一性校验
3. 手机号格式校验
4. 密码强度校验（至少 8 位，包含字母和数字）
5. 密码 BCrypt 加密存储
6. 注册成功后发送欢迎邮件（异步）

# 代码规范
- 遵循阿里巴巴 Java 开发手册
- 使用 RESTful API 设计风格
- 统一异常处理（@ControllerAdvice）
- 统一响应结果封装（Result<T>）
- 参数校验使用 @Valid + 自定义注解
- 添加完整的 JavaDoc 注释
- 日志使用 Slf4j

# 输出格式
请按以下顺序输出：
1. 数据库表结构 SQL（包含索引）
2. Entity 实体类
3. DTO 数据传输对象
4. Mapper 接口
5. Service 接口和实现类
6. Controller 控制器
7. 统一异常处理类
8. 统一响应结果类
9. 自定义校验注解

# 约束
- 禁止使用 System.out.println，统一使用 log
- 所有外部调用必须添加超时控制
- 敏感信息（密码）不能出现在日志中
- 邮件发送失败不影响注册流程
```

## 七、多轮对话上下文管理

### 7.1 复杂需求拆分技巧

**场景：** 需要一个完整的微服务模块

**❌ 错误做法：** 一次性要求生成所有代码

```
用户：帮我生成一个完整的订单微服务
```

**问题：** 
- 上下文超长，AI 遗忘前面的要求
- 输出截断，代码不完整
- 难以调试和修改

---

**✅ 正确做法：** 分步提问，保持上下文连贯

```markdown
# 第一轮：数据库设计
"作为数据库专家，设计订单微服务的表结构，包含订单主表、订单项表、订单日志表"

# 第二轮：Entity 层
"基于上面的表结构，生成 JPA Entity 实体类，使用 Lombok"

# 第三轮：Repository 层
"为这些 Entity 生成 Spring Data JPA Repository 接口，包含自定义查询方法"

# 第四轮：Service 层
"生成 OrderService，包含创建订单、查询订单、取消订单三个核心方法"

# 第五轮：Controller 层

## 九、常见错误与避坑指南

### 9.1 错误 1：需求描述模糊

**❌ 错误示例：**
```
"帮我写个接口"
```

**✅ 正确做法：**
```
"帮我写一个用户查询接口，要求：
- GET /api/users/{id}
- 返回用户基本信息（不包含密码）
- 用户不存在时返回 404
- 添加 Swagger 文档注解"
```

---

### 9.2 错误 2：技术栈不明确

**❌ 错误示例：**
```
"生成数据库访问代码"
```

**✅ 正确做法：**
```
"使用 MyBatis-Plus 3.5 生成 UserMapper 接口，要求：
- 继承 BaseMapper<User>
- 添加自定义方法：findByUsername
- 使用 @Select 注解而非 XML"
```

---

### 9.3 错误 3：忽略边界条件

**❌ 错误示例：**
```
"写一个除法方法"
```

**✅ 正确做法：**
```
"写一个除法方法，要求：
- 处理除数为 0 的情况（抛出 ArithmeticException）
- 处理 null 值（抛出 IllegalArgumentException）
- 保留 2 位小数，四舍五入
- 添加单元测试"
```

---

### 9.4 错误 4：一次性要求太多

**❌ 错误示例：**
```
"帮我做一个完整的电商系统"
```

**✅ 正确做法：**
分步骤提问：
1. 先设计数据库
2. 再生成用户模块
3. 再生成商品模块
4. 再生成订单模块
5. 最后集成测试

---

### 9.5 错误 5：不验证 AI 输出

**⚠️ 重要提醒：**
- AI 生成的代码可能有 bug
- AI 可能编造不存在的 API
- AI 可能忽略安全漏洞

**✅ 正确做法：**
1. 仔细阅读每一行代码
2. 本地运行测试
3. 进行代码审查
4. 补充缺失的异常处理
5. 验证 SQL 的正确性
